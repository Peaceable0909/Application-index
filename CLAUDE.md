# Working in this repo

## UI conventions

- **No emoji as icons, ever.** Every icon in the interface is an SVG from `src/components/Icon.tsx` (`<Icon n="check" />`). Need one that is missing? Add a path to that file instead of typing a symbol or emoji into the markup. That includes check marks, crosses, stars, sparkles and arrows used as icons (plain arrows inside a sentence are fine).
- The only emoji allowed are ones people choose to send: the chat emoji keyboard, message reactions, call reactions and the sticker pack. They are message content, not interface.
- Text the app writes into chats ("Photo", "Voice call · 2:31") stays plain words. `src/lib/sysText.ts` shows older rows without their emoji prefix and draws call lines with an icon.
- **A button that starts slow work (an email, a Google Meet link, a sheet write) must show it is working and refuse a second click.** Use `<Btn>` (spinner, disabled while the form action runs), say what is happening if it can take more than a few seconds (`SlotForm`'s working panel is the model), and make the server action safe against a double submit anyway (`doubleSubmit.ts`: interview sessions, offer emails, password reset links, stage reordering): a second click must never create a second record or send a second email. After a result, scroll the message into view (`FlashScroll`) and reset the form so it cannot be sent again by accident. The page-wide "Working…" pill and dimming (`NavProgress`) start on every form submit and link click and end when the new page arrives; `Btn` tells it when its action finished (`wr-form-done`), and the button's own spinner or anything inside the sent form never counts as the page arriving. A button that is not inside a form (`PickButton`) fires `wr-busy` with a label **before** starting its transition (updates made inside an async transition are held back until it ends) and `wr-form-done` after. Give every slow form a plain-words `data-busy` label, and a `PendingNote` when the wait is long or it emails someone.
- Anything `position: fixed` (sheets, dialogs, toasts) must not sit inside an element that keeps a `transform` after its entrance animation, or it gets pinned to that element instead of the screen. Entrance animations on page containers use `backwards` fill, not `both`.

## Messaging and calls

- Chats and calls use short "look again now" nudges (`src/lib/realtime.ts`, listener `src/components/RealtimeNudge.tsx`, Supabase Realtime broadcast on a hashed channel per person). A nudge carries no content, only `msg`, `ring` or `call`; the app then asks the server what happened. Anything that creates a message or call should nudge the other side, and nothing may depend on the nudge arriving (the regular refresh stays as the safety net).
- Student conversations for staff live in the WhatsApp-style messenger at `/inbox` (`StaffMessenger` around `ChatThread`). Send people there, not to the old Messages tab, from alerts and links.
- Attachments over ~3.5 MB go straight from the browser to the `chat-files` bucket (`src/lib/directUpload.ts`, `/api/thread/upload`), because a request to the server only carries ~4 MB. The bucket limit is 20 MB (migration 032). The GIF tab searches GIPHY through `/api/gif/search` and needs `GIPHY_API_KEY` in Vercel; without it only "From your phone" works.
- Students can set their own profile picture (`portal_student_profiles`, migration 031). Show it with `studentPhoto(s)` wherever a student appears to staff.

## Workspaces (countries)

- Every student belongs to one **workspace** (`portal_applications.workspace`, default `uk`). Staff open only the workspaces in `portal_staff.workspaces` (admins: all). The switcher in the top bar sets a cookie; `currentWorkspace()` (`src/lib/workspace.ts`) is the one place to ask which one a request is in.
- **Every list or count over students, or over anything that belongs to a student, must be scoped to the workspace.** On `portal_applications` use `.eq('workspace', ws)`. On child tables (tasks, reminders, activity, notes, documents, doc scans/text, student messages, cred attempts, folder suggestions) join with `portal_applications!inner(...)` and add `.eq('portal_applications.workspace', ws)`. A single student opened by id is already protected by `canAccessApp` / `guardApp` (use them on every page, action and API route that takes an application id).
- Jobs with no signed-in person (cron, sync, digests) never call `currentWorkspace()`: they loop `listWorkspaces()` and pass the key explicitly (`loadStudents({ workspace })`, `refreshTasks(rows, ws)`).
- Brain notes, interview slots and credibility questions have their own `workspace` column. A student sees the ones of their own workspace (`me.apps[0].workspace`).
- A `student_key` for a non-default workspace is prefixed `"<ws>:"`, so the same person in two countries is never merged.

## AI Brain, new-student chat, memory

- The Brain (`src/lib/brain.ts`) drafts replies from one student's file, the workspace's brief, notes and uploaded files (`portal_brain_docs`, passages picked by `src/lib/brainDocs.ts`), the student's memory, and where the student is in their school's stage workflow (`applicationStage`, built by `src/lib/brainStage.ts` from the same student-safe tracker as the student dashboard: current stage and its plain-words meaning, next stage, the documents asked now and where each stands, whether the student was emailed; never staff hints or review notes). The pipeline status is `facts.pipelineStatus`, the workflow stage is `applicationStage`: keep them apart. It sends no names, emails or phone numbers to the model. Opt-in with `AI_BRAIN=on`. Automatic replies (`src/lib/autoReply.ts`) are a per-workspace switch, off by default; automatic messages are `by_ai` and shown with an "AI assistant" tag.
- Memory (`src/lib/memory.ts`): after a student's new messages the last 80 messages are re-read and merged into `portal_student_memory` (a rolling summary plus a lasting `facts` list that is kept until the student contradicts it) and one pinned note (`portal_notes.ai_key = 'memory'`, author `ai`). Notes with an `ai_key` are replaced, never piled up. When a reply is drafted, `src/lib/brainRecall.ts` also searches the student's whole older history (deleted messages excluded) for what matches their latest question, rare words counting for more than common ones, and passes it as `earlierConversation`; it is plain word matching, so a message worded very differently is not found.
- The new-student chat is public: `/hello/<workspace>` and `/api/hello/*` are open in `middleware.ts`, closed per workspace until an admin switches it on (`portal_workspaces.lead_chat`). It needs consent, is rate limited, has its own AI budget (`LEAD_DAILY_LIMIT`), takes contact details from what the visitor typed (not from the model) and never sees student data. Staff answer on `/leads`; a person's reply pauses the assistant for that chat.

## Document reader

- Passports are read exactly from their machine-readable lines (`src/lib/mrz.ts`, ICAO 9303 check digits): no AI call, and the passport text never leaves the portal. Everything else is read by Drive OCR (Apps Script `extractText`) and understood by the AI after `redactForAi` hides ID-like strings. `portal_doc_scans.method` is `mrz`, `ai` or `unreadable`; the Documents page reports the split so we only add a stronger OCR server if too many files are unreadable.
- "Check all" reads three files at a time (`scanNext` in `src/lib/scanQueue.ts`).

## Sign-in security

- Staff identity goes through one gate, `staffGate()` in `src/lib/auth.ts` (`requireStaff` / `currentStaff` are built on it). It answers `ok`, `enroll`, `needs2fa`, `expired` or `none`; never read the session yourself to decide if someone is staff.
- Two-step sign-in is Supabase MFA (TOTP authenticator app). It is optional per person; an admin can make it required for admins or everyone (`portal_settings.two_step`, Settings → Sign-in security). Anyone with a verified factor must reach `aal2` in each session. `TWO_STEP_DISABLED=1` in Vercel is the emergency off switch.
- Time limits live in `src/lib/session.ts` (`SESSION_IDLE_MINUTES` default 60, `SESSION_MAX_HOURS` default 12). The `wr_act` cookie is written only by sign-in and by `IdleLock` through `/api/session/touch` (after real input), never by background polling or `router.refresh()`; middleware turns an old cookie into the `x-wr-idle` header that the gate reads.
- Every staff open or download of a document through `/api/files/[fileId]` is written to `portal_audit` (`doc_opened` / `doc_downloaded`, one line per person per file per 10 minutes). Students opening their own files are not logged.

## Reports, weekly summary, voice notes

- `src/lib/funnel.ts` (database loading) and `src/lib/funnelCore.ts` (the pure counting) are the one place that counts the road from chat to enrolment (chats in `portal_leads`, students in `portal_applications`, "reached an offer" = current status at or past Offer Received, or ever having had one in `portal_activity`). Reports page, its CSV and the weekly email all use it, always with the workspaces the viewer may open.
- The Monday management summary (`src/lib/weeklyReport.ts`, settings key `weekly_report` in `portal_settings`) is sent by the daily `/api/sync` job on Mondays, once per week, only when an admin switched it on in Settings. No icons or emoji in it.
- Voice notes are written down by `src/lib/voice.ts` through `src/lib/stt.ts` (any "audio/transcriptions" API: Groq by default, `STT_BASE_URL` / `STT_MODEL` to change). Opt-in with `AI_VOICE=on` and `STT_API_KEY` in Vercel; the recording leaves the portal, so it is off by default. The words are kept in `portal_student_msgs.transcript` (shown to the team only; the Brain, memory and inbox search use them after names, numbers and links are stripped). Automatic replies never answer a voice-only message.

## Stage workflows (Stage Mover)

- Each school has its own workflow of stages (`portal_workflows` → `portal_stages` → `portal_stage_reqs`, migration 050), per workspace. The database is the source of truth: `src/lib/stageTemplates.ts` only holds the starting points (RCL, CCCU, BPP, YSJ) that migration 050 seeded and that "Add a school" on `/workflows` can copy. Never hardcode a stage list in code; add or change stages on the Workflows page (admin only).
- The stage sits on top of the pipeline status: `portal_applications.stage_key` / `stage_at` / `stage_by` are portal-only (the sheet sync never touches them). A stage's `maps_status` sets the pipeline status when the application enters it, and `writeBack` (`src/lib/sheetWrite.ts`) puts that status in the master sheet. A null `stage_key` means "before the workflow starts": the card suggests a stage from the existing status (`suggestPlacement`), and `placeByStatus` (admin, `/stages`) places many at once without changing any status. Changing an application's school clears its stage and an undo restores it (`resetStage` / `restoreStage` in `moveCore.ts`).
- `src/lib/stageEngine.ts` is pure TypeScript (no imports, no database) so the browser runs the same rules as the server; `stageCore.ts` is the only writer (move, place, review, flags, extra requirements) and `stageActions.ts` / `workflowActions.ts` are the server actions around it. The server re-checks everything the screen showed. Tests: `npx tsx scripts/tests/stageEngine.test.ts` and `stageCore.test.ts` (against the in-memory database in `scripts/tests/mockdb.ts`).
- A stage's requirements are what must be true to **leave** it. Kinds: `document`, `confirmation`, `outcome` (a recorded result such as an interview; only the pass options count). Need: mandatory, optional or conditional (`cond:<circumstance>` set per student on the Stage tab, or `stage:<key>` = applies when that stage applies). `satisfied_at` says how far a document must get: `uploaded`, `approved` (the default) or `accepted` by the school. **An upload never satisfies a requirement by itself**; someone reviews it (requested, received, reviewed, approved, rejected, accepted). A new file after a review or rejection resets it to "uploaded", and a document already approved for another stage carries over (`carriedFrom`).
- Moves (`checkMove`): forward moves must clear every blocker on the way (including skipped stages); backward moves need a note; "move anyway" needs a role in the workflow's `override_roles` (default admin) and a written reason, and the history keeps what was open; per-stage `move_roles` apply with no override. Moving into a conditional stage switches it on for that student. Every change is in `portal_stage_history` and `portal_activity`; the pipeline status, the Offer & visa tab (`offer_sync`) and the counselor / admins (per stage `notify`) follow.
- A stage an admin switches off stays visible for applications sitting in it (it asks for nothing) so they can be moved on; requirements are switched off rather than deleted once any application has been reviewed against them.
- Students see only what their current stage asks of them (`studentAsks` → `src/lib/stageStudent.ts`, shown on `/student/documents`); uploads go through `studentUpload` with `reqType` so the file is filed exactly as asked.
- Screens: `StageCard` (application page, above the tabs), `StageSheet` (the "Move to next stage" panel), `StageDetails` (the Stage tab), `ReqRow` (one requirement), `/stages` (tracker, loaded in a few batched queries by `src/lib/stageBoard.ts`; counselors see only their own students) and `/workflows` (admin). Overdue stages, documents holding up a stage and "ready to move" become tasks (`stageTaskDrafts`, kinds `stage_late`, `stage_docs`, `stage_ready`).
- **Telling the student is a separate, optional action.** Moving a stage never emails anyone outside the team. After a move (and any time from the stage card or the Stage tab) a counselor or admin can press "Inform student" (`InformStudent.tsx`): the email is drafted from the student's name, school, the new stage, the stage's `student_note` and the documents the student must send (`stageEmailText.ts`), can be edited and previewed as the student will see it, and always goes to the address on the application (nobody types an address). It reuses the portal's one email path: `sendMail`, the `portal_messages` log, the student's in-portal notice (`addNotice`) and an activity entry (`stage_informed`). `src/lib/stageInform.ts` records who, when, to which address and whether it worked on the stage-history row itself (`inform_state` sending / sent / failed, migration 051); one atomic claim per stage change means a double click, a second tab or a retry cannot send it twice, only the application's current stage change can be announced, and a failed send leaves the stage alone and can be retried. Tests: `scripts/tests/stageInform.test.ts`.
- **The student's dashboard follows the stage, whether or not an email was sent.** `src/lib/studentStages.ts` (pure part: `studentTracker.ts`) builds, for each school the signed-in student applied to, that school's own route with completed / current / next / coming-up stages, the stage's plain-words `student_note` and the stage's student-visible documents with a student-language status. It reads only `me.apps` (found from the sign-in email) and never shows staff hints, review notes, overrides or confirmations. Moving a stage revalidates `/student` and sends a silent `stage` nudge so an open dashboard refreshes (`StageLive.tsx`); the nudge is not a notification. Edit the student wording per stage on the Workflows page.
- The seeded document lists for CCCU, BPP and YSJ are starting assumptions (Passport, Degree Certificate, Transcript, IELTS optional): the schools' real lists belong on the Workflows page.

## Assignment and routing (counselor responsibilities, Team Heads)

- **Who owns a new application** is decided by responsibilities ("rules", `portal_assign_rules`, migration 053), set by admins on `/assignments` with no code change. A rule says a counselor is the primary or a backup for one **school**, a whole **destination** (a workspace, so a new country such as Japan is just a new workspace plus a rule), or a **location** (the student's normalised city), for either **receiving the application** or **receiving and processing its documents** (`kind` application / documents). Several counselors and several rules per counselor are normal. Never hardcode a school, country or counselor; schools are matched through `schoolKey()`, destinations by workspace key.
- **Order is fixed** (`src/lib/assignEngine.ts`, pure and tested): school, then destination, then location, then nobody (the Team Head / admin queue). Inside one level one available primary wins; no primary and one backup, the backup wins; two different primaries (or two backups) is a **conflict**: flagged in `portal_assign_conflicts`, never chosen at random, resolved by a person. A paused (`paused_until`, back on from that date), switched-off or deactivated counselor's rule is skipped and the next level is tried, and the reason says so.
- **Automatic routing** (`routeApplications` in `src/lib/assignCore.ts`) runs for every application seen for the first time: in `syncWorkspace` (sheet/form intake, so it happens on the webhook-triggered sync, not when someone opens a page), "Add student" and "convert lead". It is once per application (`routed_at`), so updating an application never routes or notifies again. **An existing owner is never overwritten**, whoever set it (sheet, student's choice, person); the form's "I don't have a counselor yet" counts as no owner (`isPlaceholderCounselor`) and the sync never lets it replace a counselor the portal already has. A destination can have `auto_route` switched off. New owners are written to the sheet (best effort, a few per run) and told through push plus the existing opt-in email (`assignNotify.ts`); admins and in-scope Team Heads get one push for what is waiting for a decision. A missed application (after `portal_settings.routing_since`) is retried on the next sync. Applications that existed before routing started are untouched; "Apply the rules to the waiting" on `/head` handles unassigned ones.
- **Every change of owner goes through `reassign` / `reassignMany`** (never a bare `update({ counselor })`) so it lands in `portal_assign_log` with who, when, from, to, why, level and rule, and an override of what the rules say is recorded as one. Same owner again is a quiet no-op (no history row, no notification). Sheet changes are recorded by `recordSheetOwner`; the sheet's word stands.
- **Team Head** is an extra on top of admin / staff / counselor, not a fourth role: `portal_staff.team_head` plus rows in `portal_head_scopes` (school, destination or location). `canAccessApp` lets a counselor-role Team Head open the students inside their scope and nothing else; `mayAssign` / `inScope` decide who may reassign what. `/head` (`headBoard.ts`, `HeadDashboard.tsx`) shows only that scope: waiting and conflicts, second look (rules point elsewhere, counselor unavailable), counselor workload, applications with stage and outstanding documents (from `loadStageBoard`), quiet ones, recent assignment activity. Admins see everything in the workspaces they open. Granting a scope also gives the person that destination if they lacked it.
- **Admin page** `/assignments` (`assignActions.ts`, admin only): rules, per-destination auto-routing switch, add destination (with its responsible counselor), Team Heads, bulk reassign with a preview of exactly who moves (finished applications stay), and "update who receives documents on existing applications". Changing a rule never touches existing applications. General access (role, workspaces) stays separate from operational responsibility (rules).
- The application page has an Assignment card (`AssignmentCard.tsx`, `loadAssignInfo`): owner, document handler, why, conflict buttons, reassign, history.
- Tests: `scripts/tests/assignEngine.test.ts` (pure rules) and `assignCore.test.ts` (against the in-memory database).
- Global CSS classes such as `.info` exist; do not name a modifier after one (use a prefixed name like `lv-info`).

## Reports page (the story page)

- `/reports` is drawn from one cohort: the applications that **started** in the chosen period (and chats started in it), followed to where they are now. Period presets (30 days to everything, default 6 months, at most 60 weeks) and a country switch sit in one row above everything and scope every chart, so the numbers agree. It is scoped to the countries the viewer may open (`workspacesFor`); `?ws=` narrows to one.
- Data: `src/lib/vizData.ts` (pure: phases, calendar, weekly columns, journey flows, portfolios, quiet buckets, pace, the plain-words insights, stage tracks) and `src/lib/vizLayout.ts` (pure geometry: Sankey, sparkline, ticks), tested by `scripts/tests/reportViz.test.ts`. The page only loads facts (`loadFacts`, `loadStageBoard`) and passes them to `components/viz/ReportsView.tsx`. `phaseOf()` is the one place that groups pipeline statuses into phases (getting started, offer, CAS, visa, enrolled, closed).
- Charts are hand-built SVG/CSS (no chart library) in `src/components/viz/`. Every chart sits in `VizCard` with a Chart | Table switch (the table is the accessible twin; tooltips never gate a number), a CSV link where one exists, hover and keyboard-focus tooltips, and a phone layout (wide pictures scroll sideways with a hint). Insight sentences are only written when the sample is big enough to mean something; sections that need data the portal has not recorded yet (source, time to offer) say how they fill in instead of drawing noise.
- Colour: the validated dataviz palette lives as CSS variables on `.rv` in `src/app/reports.css` (ordinal blue ramp for how far along, four categorical slots for universities, a heat ramp), restepped for the dark theme and validated against the portal's card surfaces. A university keeps its colour whatever the period (slots follow all-time volume). Do not hardcode hex in the components; do not name a modifier class after a global one (`.info`, `.good`...): use `t-info` style prefixes.

## New-student chat engine

- One turn is `runLeadTurn` in `src/lib/leadEngine.ts`; `src/lib/leads.ts` only wires it to the database, the model and the notifications (`LeadIO`), and `src/lib/leadProfile.ts` holds the model-free logic (profile fields, greeting / "yes" / "talk to a person" detection, what to ask next, and every check a drafted reply must pass). Test the engine with fake `LeadIO` (no database needed).
- The assistant writes plain text from a real message history (`generateText`, Apps Script `aiChat` with `messages`); a second JSON call extracts the visitor's profile (`portal_leads.profile`: name, country, school, programme, level, qualifications, previousSchool, other) and only keeps what the visitor actually typed. Contact details and a clearly stated name are read without a model.
- **The assistant may never say that something was sent, passed on or arranged.** Replies that do are rejected and rewritten (`claimsAction`). Only the engine says so, with fixed wording, after `notifyHandover` really delivered (push or email to the team) and the lead was flagged (`handover_at`, `handover_delivered`). If notifying fails the visitor is told so honestly. When the model fails or the AI is off, the visitor gets an honest "I could not answer that", never a handover claim, and `needs_human` is only ever set by a real handover request.
- Facts come only from the country brief, team notes, uploaded files and the document list; anything else is "I cannot confirm that", logged in `portal_chat_gaps` (shown on the Brain page) so the team can teach it. No dashes, emoji, links, contact details, invented figures or outcome promises in replies.

## Public front page (/welcome)

- `/welcome` is open to everyone (`middleware.ts` lets `/welcome` and `/welcome/*` through). It is also the front door: a signed-out visitor who opens the bare address `/` is shown it (middleware rewrite, the address stays `/`). Signed-in people at `/` get their usual page, the installed app starts at `/student`, and the separate student address (`STUDENT_HOST`) still goes straight to the student sign-in. To undo, remove the `pathname === '/'` rewrite in `middleware.ts`.
- The whole page is one film that follows the scroll, and the information is written into the white space around the person as she moves. The film is the student's own video cut into 183 WebP stills (`public/welcome/frames/f001.webp` ...; cut with `scripts/welcome-frames.sh video.mp4`; `scripts/welcome-camera.mjs` re-measures the white space; the current stills come from the "clearer" video and were cleaned of its star watermark by `scripts/welcome-unstar.cjs`). `ScrollStory.tsx` draws the still that matches the scroll position on a full-screen canvas.
- `content.ts` holds everything that is not layout: `PANELS` (the words, and which side of the picture each sits on), `TIMELINE` (how much scrolling each stretch takes and which frames it covers: the film slows down while a panel is read and speeds through the parts with no spare room), `CAMERA` (how far the picture slides sideways, as a share of the screen, to open more white space; it was worked out from the pictures by measuring free space per frame, and the uncovered strip is the picture's own edge stretched, so there is no seam) and `FOCUS` (phones show a narrow slice of the film, so it follows her). A different video needs new stills, `FRAME_COUNT`, and new `TIMELINE`, `CAMERA`, `FOCUS` and `still` numbers.
- Wide screens (`min-aspect-ratio: 3/2` and 900 px or more) write bare text into the white space. Everything narrower or squarer puts each panel in a card low on the screen; panels that sit side by side on a wide screen then follow each other.
- The stills are cached by browsers for a year under a versioned address (`FRAMES_VERSION` in `frames.ts`). **Bump it whenever the stills are replaced**, or returning visitors keep seeing the old film.
- Stills are fetched nearest-first (the first 24 at once, the rest after the first scroll), and only a short window is kept decoded (a decoded 1600 px still is ~6 MB, phones cannot hold all of them).
- People with "reduce motion" (and anyone with scripts blocked) get the same scenes as plain pictures and text (`.wl-still`), with no canvas and no film download. Inactive panels are `inert`, so only the visible one can be tabbed to.
- Keep the words to things WhiteRock really does: no figures, no promises about results. The universities line is per workspace (`UNIVERSITIES`); a country without an entry shows no such panel.
- The chat buttons use the same bubble as any website (`/chat-bubble.js`, `data-src="website"`) and only appear for a country whose chat an admin switched on. Sign-in links on that page are plain `<a>` (not `next/link`) so the bubble, which lives outside React, is gone after leaving the page.

## Profiles, cover photos and badges

- A profile is the `portal_staff` row (migrations 010, 054) shown by `ProfileHero` (cover, picture, name with badges, professional title, bio). `/profile` edits your own (`ProfileEditor`), `/team` lists everyone, `/team/[email]` is one person's page (any signed-in team member may open it; admins also get edit panels for another person). Do not build a second profile system: new profile data goes on that row or is read from where it already lives.
- **Operational responsibility is never stored on the profile.** The countries, schools and locations someone handles (and what they oversee as Team Head) are read from the assignment records, `portal_assign_rules` and `portal_head_scopes`, by `buildHandles` (`src/lib/profileHandles.ts`, pure, tested) through `loadHandles` / `loadHandlesMap` (`profileData.ts`). `HandlesCard` has no edit button; the Responsibilities page is the one place to change it. The profile's own text fields (`responsibilities`, `duties`, `also_supports`, `bio`, `title`) are descriptions only: nothing reads them for routing or access.
- **Profile text and badges never grant access.** Access comes from the role, the workspaces, the assignment rules and Team Head scopes (`canAccessApp`, `mayAssign`), nothing else. No permission check may read a badge, a title or a duty text.
- Cover photos: `cover_url` (public bucket `covers`, 2 MB, random file names, written only by the server in `profileActions.ts`), `cover_pos` (0 to 100, which part of a tall photo shows), `cover_preset` (one of the built-in covers in `src/lib/covers.ts`, used while there is no photo; none chosen = drawn from the accent colour). The browser shrinks the photo (`CoverEditor`, at most 1600 × 1100 JPEG); the server checks the real file type from its first bytes (`sniffImage`: JPEG, PNG, WebP only, never SVG), the size, and who is asking (yourself, or an admin for anyone). Old files are deleted by `coverPathFromUrl`, which refuses any address that is not in the covers bucket. Draw covers with `<Cover>` (never an inline `background`), so the photo, the built-in covers and the shade that keeps a picture readable stay in one place.
- Admins can lock profile fields (Badges page, "Who can edit what on a profile": `portal_settings.profile_edit`, `profileRules.ts`, `profileLocks.ts`). A locked field is read-only for staff and counselors, left off their form, and kept at its stored value by `saveProfile`; admins are never locked. Add a new lockable field to `LOCKABLE` and `profileTextPatch`.
- **Badges** (`portal_badges`, `portal_staff_badges`, `src/lib/staffBadges.ts` pure and tested; the older `src/lib/badges.ts` is the student milestone badges, a different thing). An admin defines each badge on `/badges`: name, meaning, one of five colours (blue, red, yellow, green, purple), which roles may hold it, on/off, and whether students see it. Five starter badges exist, switched off and without a meaning. A badge cannot be switched on without a meaning, and it shows **only** the name and the meaning the admin wrote: never write "verified", "official" or similar into code or copy unless an admin wrote it as a meaning. A badge is drawn only while it is on and its holder's role is eligible (`visibleBadges`).
- Show a badge next to a name with `<Seals list={...} />` (`src/components/Seal.tsx`), never a hand-made icon. Staff badges come with `loadPeople()` (`person.badges`, used by `<Who>`), `badgesOf(email)` and `loadBadgeMap()` (one cached read per request); badges students may see come from `loadStudentBadgeMap()`. The tooltip is one global `BadgeTips` (in the layout) reading `data-bdg / data-name / data-desc`, so hover, keyboard focus and tap all work and nothing is clipped by a card. The five colours are tokens in `src/app/profile.css` (`--bd-*`, checked for contrast on light and dark cards; yellow carries a dark edge on light). Do not name a modifier after a global class.
- Badge and profile changes are written to `portal_audit` (`badge_created`, `badge_saved`, `badge_deleted`, `badge_assigned`, `badge_revoked`, `cover_changed`, `profile_edited`, `profile_rules_saved`). The actions are safe to repeat: giving, taking back and saving set a state, and a badge name exists once (`portal_badges_name`).
- Tests: `npx tsx scripts/tests/profileBadges.test.ts` (badge rules, covers and image sniffing, handles from assignment rules, edit locks).

## Backups

- `runBackup` (`src/lib/backup.ts`) writes one private file a night (`portal-YYYY-MM-DD.json.gz`, the portal's own data, not the sheet or Drive) and deletes the older ones. **How many are kept is an admin setting** (`portal_settings` key `backup_keep`, Settings → Backups, 3 to 90, 14 until changed), read by `backupKeep()`; `pruneBackups()` is the one place that deletes, and it only ever touches names that match `portal-YYYY-MM-DD.json.gz` (`expiredBackups` in `backupRetention.ts`, pure and tested). Saving a smaller number prunes at once. Never hardcode a keep number or delete from the `backups` bucket anywhere else.
- Tests: `npx tsx scripts/tests/backupRetention.test.ts`.

## Privacy policy (/privacy)

- `/privacy` is public (`pathname === '/privacy'` in the `pwa` list in `middleware.ts`, so the separate student address serves it too) and is written from what the portal really does: what is collected, who sees it, every AI use, every outside service, cookies and stored settings, how long things are kept. It is linked from both sign-in pages, the `/welcome` footer, the new-student chat's consent line (`LeadChat.tsx`, opens in a new tab) and the student "Me" page.
- **When you add a feature that collects new data, calls a new outside service, sets a cookie or stores something in the browser, add it to `src/app/privacy/page.tsx` (sections 2, 5, 6 and 10) and change `UPDATED` in the same change.** The policy must never claim something the code does not do (no recorded calls, no analytics, automatic AI replies always labelled); check the code before editing a sentence.
- The number of nightly backups kept is read live from `backupKeep()`, so it follows the admin setting. The contact address is one constant (`CONTACT`) in the page; the standalone form's `privacy.html` (separate repo) uses the same address and should be kept consistent with it.
- The page's CSS classes use the `pp-` prefix on purpose: `.pv`, `.pv-bar`, `.pv-page` already belong to the document previewer in `globals.css`. Below 640 px the two tables turn into stacked cards (`data-label` on each cell).

## Android app (Google Play)

- The app is a **Trusted Web Activity** in `android/` (package `com.whiterock.portal`, opens `/student` on the portal address, Android 7+, target SDK 36). It is only a frame: every feature is the website, so a portal change reaches the app at once and Play needs a new release only when the app itself changes. Do not rebuild features natively and do not run `bubblewrap update` (it overwrites `app/build.gradle`). `android/README.md` is the owner's step-by-step guide; `android/store/` holds the listing text, Data safety answers, icon, feature graphic and screenshots.
- **The signing key is never in the repository.** `app/build.gradle` reads `ANDROID_KEYSTORE_FILE`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD` from the environment (or `-P` flags); `.gitignore` blocks `*.keystore` and `*.jks`. Every release needs a higher `-PversionCode`. `.github/workflows/android.yml` builds the same thing on demand from four repository secrets.
- **Digital Asset Links** (`/.well-known/assetlinks.json`, `src/app/.well-known/assetlinks.json/route.ts`, public in `middleware.ts`) is what lets Android open the portal full screen. It lists the SHA-256 fingerprints an admin saved in Settings, Android app (`portal_settings` key `android_app`, plus `ANDROID_CERT_SHA256` in the environment), built and checked by `src/lib/androidApp.ts` (tested by `scripts/tests/androidApp.test.ts`). Google re-signs uploads, so the fingerprint that matters is the **app signing key** from Play Console, not the upload key. Never list a debug key. Without a fingerprint the app still works but shows a browser bar.
- The same Settings card stores the Google Play link; the student "Me" page then shows a "Get the app on Google Play" button to Android visitors (`InstallApp`).
- The web manifest (`src/app/manifest.ts`) has a stable `id`, a separate maskable icon, shortcuts and the `related_applications` entry; the PWA and Android icons are the generated W mark (`android/store/icon-mark.svg`, redrawn by `android/tools/render-icons.cjs`), a placeholder like the other square icons.
- Anything that changes what data the app handles also goes into `src/app/privacy/page.tsx` and `android/store/data-safety.md`.
